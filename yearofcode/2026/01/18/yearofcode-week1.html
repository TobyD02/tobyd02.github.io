YOC - Week 1: Finding Motivation

Jan 18, 2026

Slow Beginnings

I wish I could stay the year started off strong – unfortunately, it’s been less productive than I would’ve hoped. Partially due to spending part of the week setting up this blog, but also due to a general lack of motivation. I think I might have overwhelmed myself with the original plan (one completed project every week). This sent me down a path of forcing myself to work every day after work – which just drained my battery of the little charge it had left.

This ended up leading to frustration, but also a dependency on AI slop - unveiling a new goal for the year which is to avoid integrating code into my codebases that I don’t understand. ChatGPT becomes my excuse for laziness - allowing me to solve problems in hacky ways, providing quick results but technical debt longterm. Due to a complete lack of awareness of how a particular component works, you end up depending on AI to add features, fix bugs, etc…

The Project

Day 1

I started off rather reluctantly, trying to scrape together some idea. I’ve developed simple TODO apps before, so I decided that it might be an easy way to get started. I started with research - looking into the different ways I could pull the data I wanted from the repositories. Naturally, I stumbled across the GitHub API, which seemed like a perfect fit - you can view commit trees, monitor events, etc… I set up my project environment, Docker images, and GitHub authentication and began playing around with some ideas.

I rather quickly hit the limits with the GitHub API - web requests have an inherent latency tied to them, which only compounds with paginated responses. For a large repo (I was using Facebook/React to test), It was taking upwards of 10 minutes to iterate through all the pages. For this reason, I started looking towards what felt like a bit more of a hacky solution - cloning the repository and using shell commands to find what I was looking for. By the end of the day, the only code I had written was some sloppy AI script which would:

  • Clone a repo
  • Run git grep to find all the files containing todos
  • Store all the todos in an array and print it out

Day 2

For the second day, I decided to avoid programming since I was already drained from working - instead I focused on getting the backend systems running and communicating. The architecture I decided on was as follows:

  • A python worker (using celery) for initial scraping of repositories, and intermittent monitoring of tracked repository - checking for new commits on any branches.
  • Redis (streams) for handling the queueing of tasks
  • Some SQL database for storing the data (likely Postgres)
  • A simple FastAPI application for serving the data.

Initially, I wanted to use sqlite for the database; since the frontend would be readonly, there would be no race conditions with the celery workers. However, this would limit me to a single worker - besides using a database engine such as Postgres removes the worry of potentially migrating in the future (I also happen to be more familiar). As for the choice to use Redis streams over something like RabbitMQ - this was primarily due to the fact that redis is a very lightweight and easy to set up interactions with. I felt that a more feature-rich message broker such as RabbitMQ was unnecessary for such a simple application.

Day 3

I was feeling much more motivated by day 3, I started off by improving the repository todo extraction. The first thing I wanted to add was branch-aware todo tracking - this was fairly simple to set up, simply query the repository for a list of the branches, check out each one, and run git grep. Next was setting up some system for monitoring if any todos had been added or removed. To do this, I capture the commit hash of each branch when I initially scrape them - then, on any subsequent processes, I compare the current commit hash to the one I captured. If it is the same - ignore it, nothing has changed - otherwise (just for the sake of a quick MVP) I delete all the stored TODO’s for that branch and re-scrape them.

Conclusion

This first week was a difficult one to get through, not necessarily because of the project itself (though it did feel a bit uninspired at times, which definitely didn’t help) - but my general lack of interest and motivation. I’m glad that I tried to push myself through it, because it really helped me to realise the flaws with my original plan for this Year of Code. Finishing a project a week is a tall order even if you dedicate all your time to it, so balancing that with work, exercise, a social life, etc… is really just not possible.

Setting ambitious goals is good - but it can also be a bit overwhelming. I realised that the goal of “1 project per week” was setting myself up for failure. At most - I could reach that goal, but more often than not I would end up finishing the week with an unfinished prototype and a feeling of disappointment. This is why I changed it - having instead a goal of “1 finished project in the year” means I will more than likely surpass my goal. For a project like the Year of Code - where the goal is to encourage myself - I think this is a much better target. I won’t lose interest because I’m coming home tired and forcing myself to work every day, instead I’ll put in the time to finish projects I’m passionate about when I have ideas.

I’m undecided as to whether I’ll continue with this project - I think it’s a solid idea; the potential is there. But currently, it’s just not that interesting to me. I’d like to explore less functional project ideas, ones that are purely creative endeavours, and then hopefully that will spark some functional ideas that I can start working on.
